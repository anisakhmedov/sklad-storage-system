# Sklad — система учёта хранения продукции в контейнерах

MVP для одного заказчика: Telegram Mini App (бот) для сотрудников склада + веб-панель
для владельца/доверенных лиц. Единый проект на **Next.js 14 (App Router, TypeScript)**,
разворачивается на **Vercel**, база данных — **MongoDB (Atlas)** через **Mongoose**,
бот — **grammy** через webhook-роут `/api/telegram/webhook` (без Docker и постоянного процесса).

## Быстрый старт локально

Требуется Node.js 18+ и доступ к MongoDB (Atlas или локальный).

```bash
npm install
cp .env.example .env.local   # заполнить переменные (см. ниже)
npm run seed                 # создаёт владельца, контейнеры и тестовые записи
npm run dev                  # http://localhost:3000
```

После `npm run seed` в консоли будет выведен логин/пароль владельца
(`OWNER_IDENTIFIER` / `OWNER_PASSWORD` из `.env.local`, по умолчанию `owner` / `change-me-123`)
— зайдите с ними на `/login`.

### Проверка Mini App без реального Telegram

Проверять `/miniapp` можно прямо в браузере, без Telegram: если `window.Telegram.WebApp.initData`
пустой (страница открыта не в Telegram) и `NODE_ENV !== "production"`, клиент подставляет
заголовок `X-Debug-Telegram-Id` со случайным id, сохранённым в `localStorage`, и сервер принимает
такой запрос как «dev-режим» (см. `lib/telegramAuth.ts` → `devBypassUser`, `lib/miniAuth.ts`).
В `npm run seed` уже создан подтверждённый тестовый сотрудник (`telegramId=111111111`) — чтобы
войти под ним локально, откройте DevTools → Application → Local Storage и задайте
`sklad_dev_telegram_id = 111111111` перед открытием `/miniapp`, либо просто пройдите
регистрацию заново со случайным id и подтвердите заявку в веб-панели (раздел «Сотрудники»).
**В production этот bypass отключён** — работает только настоящая проверка подписи initData.

## Переменные окружения

См. `.env.example`. Кратко:

| Переменная | Назначение |
|---|---|
| `MONGODB_URI` | строка подключения к MongoDB (Atlas или локальный) |
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather |
| `TELEGRAM_WEBHOOK_SECRET` | секрет для проверки заголовка `X-Telegram-Bot-Api-Secret-Token` от Telegram |
| `APP_BASE_URL` | публичный URL приложения (для ссылки на Mini App и регистрации webhook) |
| `NEXTAUTH_SECRET` | секрет для подписи JWT-сессии веб-панели |
| `OWNER_IDENTIFIER` / `OWNER_PASSWORD` | используются только `scripts/seed.ts` для создания первого владельца |

## Подключение Telegram-бота

1. Создайте бота через [@BotFather](https://t.me/BotFather) → `/newbot`, получите токен.
2. Пропишите токен в `.env.local` (локально) и в переменных окружения Vercel (для прода).
3. После деплоя на Vercel задайте `APP_BASE_URL=https://<ваш-домен>.vercel.app` и выполните:
   ```bash
   npm run set-webhook
   ```
   Скрипт одним запуском регистрирует webhook на `https://<APP_BASE_URL>/api/telegram/webhook`
   (с секретом из `TELEGRAM_WEBHOOK_SECRET`, если задан), список команд бота (`/start`,
   `/report`, `/contract`, `/help` — видны в системном меню "/") и постоянную синюю кнопку
   меню рядом с полем ввода, которая открывает `APP_BASE_URL/miniapp` напрямую — сотруднику
   не нужно сначала писать `/start`, чтобы попасть в приложение (кнопка со ссылкой на Mini App
   также по-прежнему отправляется ботом в ответ на `/start`, см. `lib/telegramBot.ts`, — это
   запасной путь, а не единственный). Ручная настройка через `@BotFather` (`/newapp`,
   `/setmenubutton`) для этого больше не нужна. Проверить текущий webhook можно через
   `https://api.telegram.org/bot<TOKEN>/getWebhookInfo`.

## Деплой на Vercel

1. Запушьте проект в git-репозиторий, импортируйте его в Vercel.
2. В настройках проекта Vercel добавьте все переменные из `.env.example`
   (окружение Production и Preview).
3. Deploy. После первого деплоя узнайте окончательный `APP_BASE_URL`, обновите эту
   переменную в Vercel (если домен ещё не был известен на шаге 2) и передеплойте.
4. Запустите `npm run seed` **локально**, указав в `.env.local` тот же `MONGODB_URI`,
   что и в Vercel (Atlas — общая база, поэтому seed из локальной машины наполнит именно
   продовую БД). Либо создайте владельца вручную через `mongosh`/Atlas UI, если не хотите
   заводить тестовые записи в проде.
5. Выполните `npm run set-webhook` (см. выше) — теперь Telegram будет слать обновления
   на serverless-функцию `/api/telegram/webhook`. Отдельный постоянно работающий процесс
   для бота не нужен.

## Роли и доступ

- **Владелец** и **Доверенное лицо** — полный доступ к веб-панели (идентичны по правам,
  доверенное лицо тоже может выдавать доступ другим). Заходят по логину (username/телефон)
  и паролю на `/login`.
- **Сотрудник** — работает только через Telegram Mini App. После первого открытия проходит
  регистрацию (имя + телефон), попадает в статус `pending`, ждёт подтверждения владельцем
  в разделе «Сотрудники» веб-панели. После одобрения может создавать записи о размещении
  товара, но не может их редактировать или удалять.
- Аутентификация веб-панели реализована на **логине/пароле** (JWT в httpOnly cookie), а не
  через magic-link — см. пояснение в разделе допущений ниже.
- **Владелец груза (арендатор)** — не роль в системе доступа, а просто человек, чьи данные
  сотрудник вносит в запись; у него нет логина/пароля и нет доступа к Mini App или веб-панели.
  Он только переписывается с тем же ботом напрямую и после подтверждения номера телефона
  получает уведомления/сводку/договор — см. следующие два раздела.

## Уведомления и сводка владельцам груза (часть 2)

Тот же бот (тот же токен, тот же вебхук) теперь общается и с **владельцами груза** —
людьми, чьи данные сотрудник вносит в `StorageRecord.goodsOwner` при регистрации товара.
Эти люди не имеют доступа к Mini App, они просто пишут боту в обычном чате. Вся логика — в
`lib/telegramBot.ts` (хендлеры апдейтов), `lib/goodsOwnerBot.ts` (идентификация, ключевые
слова, тексты) и `lib/telegramNotify.ts` (исходящие уведомления из API Mini App).

**1. Идентификация по номеру телефона.** Когда ещё не опознанный ботом человек (не
сотрудник, нет привязки) пишет `/start` или любое сообщение, бот присылает кнопку Telegram
«📱 Отправить номер телефона» (`request_contact`). После того как пользователь делится
контактом, бот сравнивает нормализованный номер (`lib/phone.ts`, формат `+998...`) с
`goodsOwner.phone` **физлиц**-арендаторов во всех `StorageRecord`. При совпадении сохраняется
связка `{ telegramId, phone, fullName, linkedAt }` в новой коллекции `GoodsOwnerLink`
(`models/GoodsOwnerLink.ts`); при отсутствии совпадений — вежливое сообщение с просьбой
обратиться к сотруднику/владельцу.

**2. Уведомление о новой записи.** Когда сотрудник в Mini App создаёт `StorageRecord` для
физлица и для его `goodsOwner.phone` уже есть `GoodsOwnerLink`, бот сразу шлёт в чат
владельцу груза:
```
✅ Ваш товар успешно зарегистрирован.
Контейнер: Контейнер №1
Товар: Яблоки, 5 т
Дата: 09.08.2026
Тариф за хранение: 250 сум/кг в месяц
```
Паспортные данные и ПИНФЛ в уведомления и сводку никогда не попадают. Если привязки ещё
нет — уведомление тихо не отправляется, ничего не падает (best-effort, см.
`lib/telegramNotify.ts`).

**3. Сводка по запросу.** Уже идентифицированный владелец груза может написать боту
`отчёт`/`сводка`/«мои товары»/«долг»/«задолженность» или `/report` (распознавание по
подстроке, без учёта регистра — `lib/goodsOwnerBot.ts` → `isReportRequest`). Бот собирает
все его записи (`lib/reports.ts` → `getGoodsOwnerSummary`, поиск по нормализованному
телефону среди физлиц) и присылает Markdown-сообщение: список контейнеров с количеством по
каждому, даты последних поступлений и — начиная с добавления тарифов — начисленную сумму,
оплаченную сумму и задолженность по каждому контейнеру и итогом (см. следующий раздел
«Тарифы, оплата и задолженность»).

### Как проверить руками

Для реальной отправки сообщений нужен настоящий `TELEGRAM_BOT_TOKEN` и зарегистрированный
webhook (`npm run set-webhook`, см. выше) — без бота эту часть можно проверить только по
коду/логам.

1. `npm run seed` создаёт (среди прочего) две записи физлица «Иванов Иван Иванович» с
   телефоном `+998901234567` в разных контейнерах — специально для проверки агрегации.
2. В Telegram напишите боту `/start` под любым аккаунтом, поделитесь номером телефона
   `+998901234567` через появившуюся кнопку.
3. Бот должен подтвердить привязку по имени «Иванов Иван Иванович».
4. Создайте ещё одну запись через Mini App с телефоном владельца `+998901234567` (тем же
   тестовым сотрудником) — бот должен прислать уведомление о регистрации автоматически.
5. Напишите боту «отчёт» — должна прийти сводка минимум по двум записям/двум контейнерам
   с суммой оплат.

## Тип арендатора и договор (часть 3)

### Физическое и юридическое лицо

При создании записи сотрудник сначала выбирает тип арендатора (`goodsOwner.type`):

- **Физическое лицо** — ФИО, телефон, номер паспорта, ПИНФЛ, дата выдачи паспорта, кем
  выдан. Для этого типа **автоматически формируется договор** (см. ниже).
- **Юридическое лицо** — наименование фирмы, ИНН, имя и фамилия директора. Данные только
  сохраняются, **договор не формируется** — никаких дополнительных шагов.

Модель `StorageRecord.goodsOwner` — дискриминированный union (`models/StorageRecord.ts`),
валидация — `z.discriminatedUnion("type", …)` в `lib/validation.ts`. И Mini App
(`NewRecordWizard.tsx`), и веб-панель (`app/dashboard/records/page.tsx`, форма
редактирования) рендерят поля условно по выбранному типу.

**Персональные данные физлиц (паспорт, ПИНФЛ) хранятся открытым текстом.** Это отменяет
решение из части 1 (там стояла заглушка/TODO на шифрование) — они подставляются напрямую
в текст договора, шифровать их на уровне поля больше не нужно. Шифрование не было
реализовано на момент этого ТЗ (было только упоминание в комментарии/README), поэтому
удалять было нечего — но комментарий убран, и README ниже переписан под новое решение.

### Как собирается PDF — и почему именно так (блокирующий вопрос из ТЗ)

В ТЗ явно было сказано спросить, если для выбора способа docx→PDF на Vercel serverless
нужен мой (пользователя) ответ. Выбор сделан самостоятельно — он совпадает с первым из
трёх предложенных в ТЗ вариантов, и других вводных, специфичных именно для этого проекта,
не требовалось:

**Договор собирается программно через [`pdfkit`](https://pdfkit.org/) — без промежуточного
`.docx` и без LibreOffice/`soffice`.** Одноразовый скрипт
`scripts/extractContractTemplate.js` (без внешних зависимостей — сам разбирает `.docx` как
ZIP через встроенный `zlib`) один раз вытащил текст `templates/contract_template.docx` в
порядке документа и классифицировал его (заголовки разделов / пронумерованные пункты /
маркированные списки / таблица реквизитов / таблица тарифа) в статический массив
`lib/contract/contractTemplateBlocks.ts`. На каждый запрос договора
`lib/contract/generateContract.ts` рендерит этот массив в PDF заново, подставляя данные
записи вместо плейсхолдеров.

Почему не два других варианта из ТЗ:
- **Внешний сервис/API конвертации docx→pdf** — лишняя внешняя зависимость (регистрация,
  ключ, стоимость, сетевой отказ как новая точка отказа) там, где задача полностью решается
  без сети.
- **Отдельный always-on процесс** — в ТЗ прямо сказано «без Docker», а вне Docker
  разворачивать и поддерживать ещё один постоянно работающий процесс только ради
  docx→pdf — избыточно для MVP одного заказчика, когда весь остальной проект принципиально
  serverless.
- **pdfkit** — чистый JS (плюс `fontkit` для шрифтов), без нативных бинарников, официально
  ставится и работает в serverless-функциях Node.js на Vercel, предсказуемый по времени и
  размеру бандла.

Компромисс: при изменении текста `.docx`-шаблона нужно вручную перезапустить
`npm run extract-contract-template` — верстка не «живёт» в самом `.docx` файле. Для одного
фиксированного юридического шаблона, который не меняется каждую неделю, это разумная цена
за надёжность на serverless.

**Шрифт.** Стандартные 14 PDF-шрифтов не содержат кириллицу вообще, а большинство
бесплатных кириллических шрифтов не содержат специфические узбекские буквы Ў/Қ/Ғ/Ҳ,
которые активно встречаются в тексте шаблона. Используется **DejaVu Sans**
(`templates/fonts/*.ttf`, лицензия — `templates/fonts/LICENSE.txt`, свободно
встраивается/распространяется) — вручную проверено, что он покрывает 100% символов,
использованных в шаблоне (кириллица, узбекские буквы, латиница, пунктуация).

**PDF нигде не хранится** — собирается заново на каждый запрос из актуальных полей записи
(включая после редактирования на веб-панели). Это осознанный выбор: контракт полностью
детерминирован данными записи, поэтому хранить копию — лишняя сущность, которая может
разойтись с записью после правки. Цена — доля секунды на регенерацию при каждом запросе,
что для PDF из текста pdfkit пренебрежимо мало.

### Подпись клиента

Для физлиц в Mini App после шагов «Тариф» мастер `NewRecordWizard` добавляет ещё два шага
(юрлицам договор не формируется — эти шаги для них не показываются):

1. **«Договор»** — сотрудник передаёт телефон клиенту, тот читает заполненный текст
   договора прямо на экране (`components/miniapp/ContractPreview.tsx`, те же
   `CONTRACT_BLOCKS`, что и в PDF, но отрендеренные как HTML). Номер договора на этом
   этапе ещё не присвоен (он выдаётся только при сохранении записи) — в превью прочерк.
2. **«Подпись»** — клиент сам расписывается пальцем/стилусом на `<canvas>`
   (`components/miniapp/SignaturePad.tsx`), результат — PNG (`canvas.toDataURL("image/png")`).

PNG уходит вместе с остальными полями в `POST /api/miniapp/records`, декодируется
(`lib/signature.ts::decodePngDataUrl`) и сохраняется как `StorageRecord.clientSignaturePng`
(`Buffer`) — обязателен для физлиц (`lib/validation.ts::storageRecordCreateSchema`,
проверка в `superRefine`). Поскольку подпись — часть данных самой записи (тот же принцип,
что и остальные поля договора), **любая** последующая перегенерация PDF автоматически
печатает её в колонке «КЛИЕНТ» поверх линии для подписи (`lib/contract/generateContract.ts::renderSignatureBlock`) —
не только сразу после создания записи, но и при скачивании с веб-панели, и по запросу
«договор»/`/contract` в чате бота.

Чисто текстовая логика заполнения плейсхолдеров (`ContractFillData`, `buildContractFillData`,
`placeholderMap`, `fill`, `formatContractDate`) вынесена в `lib/contract/placeholders.ts` —
файл намеренно не импортирует `pdfkit`/`path` (в отличие от `generateContract.ts`), чтобы его
можно было безопасно импортировать из браузерного `ContractPreview.tsx`.
| `<Имя сокрощенное. Фамилия>` (в блоке подписи, колонка «КЛИЕНТ») | сокращённое ФИО арендатора: `"{первая буква имени}. {фамилия}"`, напр. `goodsOwner.fullName = "Ахмедов Анисхон Равшанович"` → `"А. Ахмедов"` — уточнено, реализовано в `abbreviateFullName()` (`lib/contract/generateContract.ts`). Ранее рядом стояло статичное «Ж.Сулаймонов» (имя подписанта со стороны «Сақловчи», ошибочно попавшее в колонку клиента) — убрано по просьбе пользователя. |

### Куда попадает готовый договор

1. **Автоматически в чат сотрудника** — сразу после создания записи о физлице в Mini App
   (`app/api/miniapp/records/route.ts` → `sendContractToEmployee`).
2. **Веб-панель** — кнопка «Договор» в разделе «Записи» рядом с каждой записью физлица
   (`GET /api/records/[id]/contract`, открывается в новой вкладке, `Content-Disposition:
   inline` — можно и посмотреть в браузере, и сохранить).
3. **По запросу арендатора в боте** — ключевое слово «договор» (аналогично «отчёту», см.
   выше) или команда `/contract`, только для уже идентифицированных владельцев груза
   (`GoodsOwnerLink`). **Если у арендатора несколько записей/договоров — отправляется
   договор по самой свежей записи**, а в подписи к файлу бот прямо указывает, что записей
   несколько и что для другого договора нужно обратиться к сотруднику (осознанный дефолт,
   не блокирующий — уточнять/выбирать конкретный договор через диалог с ботом не стали ради
   простоты MVP).

### Как проверить руками

1. `npm run seed` создаёт юрлицо-запись (без договора) и несколько физлиц — в том числе
   двух «Иванов Иван Иванович» на одном номере (для проверки «самый свежий договор»).
2. Через Mini App создайте запись с типом «Физическое лицо» — сразу после сохранения в чат
   **сотрудника** (тестовый аккаунт, под которым открыт Mini App) должен прийти PDF.
3. На веб-панели (`/dashboard/records`) у этой записи должна появиться кнопка «Договор» —
   открывает PDF; у записей юрлиц кнопки нет.
4. Привяжите в боте номер `+998901234567` (см. предыдущий раздел) и напишите «договор» —
   должен прийти PDF по самой свежей из двух записей на этот номер, с пометкой, что записей
   несколько.
5. Откройте PDF и проверьте: кириллица (включая узбекские буквы) отображается корректно,
   все плейсхолдеры заменены, включая сокращённое имя арендатора в колонке «КЛИЕНТ» блока
   подписи (напр. для «Иванов Иван Иванович» ожидается «И. Иванов»), и что «Ж.Сулаймонов»
   там больше не выводится.

## Тарифы, оплата и задолженность

Раньше сотрудник сразу при создании записи вводил разовую «сумму оплаты». Это заменено на
двухчастную схему, потому что арендатор часто платит не сразу и не всей суммой:

1. **Тариф** (`StorageRecord.tariff = { type, rate }`) — договорённые условия, фиксируются
   один раз при создании записи (Mini App) или правятся на веб-панели. Это НЕ факт оплаты.
2. **Оплата** (`models/Income.ts`) — фактически полученные деньги, вносятся отдельно и когда
   угодно через веб-панель (`/dashboard/income`, пункт меню «Оплаты»). Одна запись может
   получить ноль, один или несколько платежей на протяжении всего срока хранения.

Задолженность (`lib/debt.ts`) = начислено по тарифу минус оплачено, и считается не по одной
записи, а по связке **владелец + контейнер** (у одного владельца может быть несколько
записей в одном контейнере — они складываются).

### Типы тарифов

| Тип | Пример ставки | Как считается начисление |
|---|---|---|
| За день (`per_day`) | 30 сум | `ставка × дней` — фиксированно за размещение целиком, количество товара не участвует |
| За месяц (`per_month`) | 9 000 сум | `ставка × целых_месяцев` — тоже фиксированно за размещение целиком |
| За кг в месяц (`per_kg_month`) | 250 сум | `вес_в_кг × ставка × целых_месяцев` |
| За кг за 6 месяцев (`per_kg_6_months`) | 1 000 сум | `вес_в_кг × ставка × целых_полугодий` |

«Целых месяцев»/«целых полугодий» — число ПРОШЕДШИХ дней делится на длину периода (30 или
180 дней) и округляется **вверх**: любой день сверху целого периода начинает новый
оплачиваемый период целиком, начисление не размазывается по дням внутри периода (см.
`lib/tariff.ts` → `wholeMonths`/`wholeSixMonthPeriods`/`accrueTariff`). Месяц принят равным
30 дням — простое и предсказуемое приближение вместо календарных месяцев разной длины.
Тарифы «за кг» переводят
количество в килограммы (`tonne` × 1000, `kg` как есть) и поэтому **недоступны** для записей
с единицей измерения «ящики»/«штуки» — вес неизвестен (проверяется и в форме, и в zod, и в
Mongoose-модели, см. `lib/validation.ts` / `models/StorageRecord.ts`). В UI (Mini App и
дашборд) эти два варианта тарифа просто не показываются, если выбрана такая единица.

Первые два типа («за день»/«за месяц») намеренно приняты как **фиксированная плата за
размещение целиком**, а не «за штуку/ящик» — в тексте ТЗ для них не было указано «за кг» в
отличие от двух других пунктов, а для ящиков/штук вес всё равно неизвестен, чтобы считать
поштучно осмысленно. Если на самом деле имелось в виду что-то другое (напр. «за ящик в
день») — это изолированная правка одной функции `accrueTariff`.

### Задолженность: с какой даты и на какую дату

Начисление по каждой записи идёт **с даты её создания** (`createdAt`) — именно так, как
попросили: «задолженность идёт от даты когда вписывают его». Правки количества/тарифа
позже применяются к тому же периоду задним числом (упрощение: без учёта истории изменений,
как в остальном проекте — история видна отдельно в `AuditLog`, но не влияет на расчёт).

Конечная дата периода — **выбирается** (поле «По дату» на `/dashboard/income`, `?to=` у
`GET /api/debts`); если не указана — берётся **сегодняшний день**. Оплаты (`Income.paidAt`)
позже выбранной даты в начисление на эту дату не засчитываются.

### Дата окончания и закрытие записи

Две отдельные, не влияющие друг на друга даты сверх `createdAt`:

- **`expectedEndDate`** — ориентир «когда клиент заберёт товар», подсказывается по тарифу
  (`lib/tariff.ts::suggestedEndDate`: `+30` дней для `per_month`/`per_kg_month`, `+180` для
  `per_kg_6_months`, ничего для `per_day`) при создании записи и редактируема. На начисление
  не влияет — это просто напоминание.
- **`closedAt`** — фактическое закрытие («товар забран», «договор расторгнут»): начисление по
  тарифу останавливается на эту дату и дальше не растёт (см. `lib/debt.ts`), даже если позже
  запрошена задолженность на более позднюю дату `to`. Закрытая запись пропадает из сводной
  таблицы «Арендаторы» (`lib/tenantMatrix.ts` фильтрует `closedAt: { $exists: false }`), но не
  удаляется — остаётся в журнале «Записи» и в расчёте задолженности (если баланс не нулевой).
  Переоткрывается тем же маршрутом (`closedAt: null`).

И то, и другое редактируется с обеих платформ: веб-панель — `PATCH /api/records/[id]`
(даты) и `POST /api/records/[id]/close` (закрытие/переоткрытие); Mini App — тот же набор под
`/api/miniapp/records/[id]` и `/api/miniapp/records/[id]/close` (проверяется доступ сотрудника
к контейнеру записи, см. `lib/miniAuth.ts::employeeCanAccessContainer`).

### Где что находится

- `lib/tariff.ts` — типы тарифов, подписи, ставки по умолчанию, формула начисления.
- `lib/ownerKey.ts` — идентификатор арендатора для агрегации: нормализованный телефон для
  физлиц, ИНН для юрлиц (у юрлиц нет телефона в схеме — тарифы и задолженность работают для
  обоих типов арендатора, в отличие от договора, который только для физлиц).
- `models/Income.ts` — фактические платежи.
- `lib/debt.ts` — агрегация начислено/оплачено/остаток по связкам владелец+контейнер.
- `app/api/debts` (`GET`), `app/api/income` (`GET`/`POST`) — API веб-панели.
- `app/dashboard/income/page.tsx` («Оплаты» в меню) — форма записи платежа (выбор владельца
  → его контейнера → суммы/способа/даты оплаты) и таблица задолженности с выбором даты «по».
  Платёж можно завести только на связку владелец+контейнер, для которой реально есть хотя бы
  одна запись (защита от опечаток — см. `app/api/income/route.ts`).
- `app/api/records/[id]/close`, `app/api/miniapp/records/[id]/close` — закрытие/переоткрытие
  записи (см. «Дата окончания и закрытие записи» выше).
- `app/api/miniapp/owners/search` — поиск уже существовавших владельцев груза по
  имени/телефону/ИНН для повторного назначения клиента в мастере новой записи
  (`components/miniapp/NewRecordWizard.tsx`, шаг «Владелец груза») — подставляет паспортные/
  реквизитные данные из его последней записи вместо повторного ввода с нуля.
- Бот: сводка по ключевым словам «отчёт»/«сводка»/«долг»/«задолженность»/`/report` теперь
  включает начислено/оплачено/остаток по каждому контейнеру и итогом (`lib/goodsOwnerBot.ts`
  → `formatOwnerSummaryMessage`). Запись о вводе товара тоже присылает тариф вместо суммы
  оплаты (`formatRegisteredMessage`).
- Запись только для физлиц/юрлиц через веб-панель или бота не разграничена по ролям —
  вносить оплату может любой владелец/доверенное лицо (как и списание/вывоз товара).

## Допущения по неоднозначным местам ТЗ

- **Способ входа в веб-панель**: логин (username/телефон) + пароль вместо magic-link через
  Telegram — проще для MVP одного заказчика и не требует привязывать вход к боту. Модель
  `WebAccess` расширена служебным полем `passwordHash` (в ТЗ не указано явно). Когда владелец
  выдаёт доступ новому пользователю (раздел «Доступ»), система генерирует временный пароль и
  один раз показывает его в интерфейсе — владелец должен передать его лично; при первом входе
  показывается баннер с предложением сменить пароль (`mustChangePassword`).
- Контейнеры создают/редактируют только владелец и доверенные лица — сотрудники только
  выбирают контейнер из уже существующего списка при создании записи.
- Оплата за хранение — это то, что владелец груза платит владельцу контейнеров; изначально
  сотрудник фиксировал сумму сразу при создании записи, теперь — только тариф (ставку), а
  сумма и способ оплаты вносятся отдельно через `/dashboard/income`, когда деньги реально
  получены (см. «Тарифы, оплата и задолженность»); деньгами в системе никто не оперирует.
- Доверенные лица получают доступ, полностью идентичный владельцу, включая право выдавать
  доступ другим и назначать роль `owner`.
- Единицы измерения зафиксированы как: тонны, кг, ящики, штуки (`tonne | kg | box | piece`).
- Списание/вывоз товара — отдельная сущность `Withdrawal`, доступна только на веб-панели
  владельцу/доверенным лицам (раздел «Отчётность» → блок «Списание / вывоз товара»).
  Остаток по контейнеру считается как `сумма поступлений − сумма списаний`, отдельно по
  каждой единице измерения (объёмы в тоннах и, например, кг намеренно не суммируются вместе,
  чтобы не создавать вводящих в заблуждение цифр).
- График «объём товара по месяцам» и «загруженность по контейнерам» показывают до 4 рядов
  (по одному на единицу измерения) на одной оси Y — это приближение для наглядности, сравнивать
  корректно только значения внутри одного ряда (одной единицы измерения).
- Аудит-лог (`AuditLog`) фиксируется для `StorageRecord`, `Container`, `Employee` (смена
  статуса), `WebAccess` и `Withdrawal` — не только для записей, как минимально требовало ТЗ,
  чтобы у владельца была полная история действий.
- Удаление контейнера запрещено, если по нему уже есть записи (защита от потери связности
  данных) — предлагается сначала удалить/перенести записи.
- **Нормализация телефона** (`lib/phone.ts`) сделана под Узбекистан: 9-значный номер без
  кода страны считается узбекским и дополняется `+998`. При выходе за пределы одной страны
  стоит заменить на полноценную библиотеку (`libphonenumber-js`).
- **`/start` для ещё неопознанного пользователя** показывает и кнопку Mini App, и кнопку
  «Отправить номер телефона» — на этом шаге бот не может знать, будущий это сотрудник или
  владелец груза, а часть 1 уже полагалась на инлайн-кнопку в чате как основной способ
  онбординга сотрудников. Показывать оба варианта — самый безопасный дефолт: он не ломает
  часть 1, но выполняет то, что явно требует часть 2 (см. `lib/telegramBot.ts`).
- **`GoodsOwnerLink`**: одна привязка на `telegramId` (upsert), но не unique по `phone` —
  теоретически один и тот же номер могут привязать разные Telegram-аккаунты (например, два
  члена семьи). При отправке уведомления/поиске по телефону используется самая свежая
  привязка (`linkedAt` по убыванию) — задокументированное упрощение для MVP.
- **Договор для физлица с несколькими записями**: и в боте («договор»/`/contract`), и по
  сути в самой идее "один арендатор — один документ" нет однозначного "того самого" договора
  — отправляется договор по самой свежей записи, с явной пометкой в сообщении, что записей
  несколько (см. «Тип арендатора и договор» выше).
- PDF договора **нигде не хранится** — генерируется заново на каждый запрос из текущих полей
  записи (см. «Тип арендатора и договор» выше).

## Безопасность

- Пароли веб-пользователей хранятся как bcrypt-хэши.
- Сессия веб-панели — JWT в httpOnly cookie (`NEXTAUTH_SECRET`), проверяется на сервере при
  каждом запросе к API и к серверным страницам `/dashboard/*`.
- Telegram Mini App аутентифицируется проверкой HMAC-подписи `initData` (`lib/telegramAuth.ts`,
  по алгоритму из [официальной документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app)) —
  подделать telegramId, не зная токен бота, нельзя.
- **Персональные данные физлиц (паспортные данные, ПИНФЛ)** хранятся в
  `StorageRecord.goodsOwner` открытым текстом — **осознанно, начиная с части 3 ТЗ**: они
  подставляются напрямую в текст договора (`lib/contract/generateContract.ts`), поэтому
  шифрование на уровне поля было бы им прямо противопоказано (пришлось бы расшифровывать
  перед каждой генерацией PDF без какого-либо выигрыша в безопасности). Это явно отменяет
  прежнее решение части 1 (там было условие зашифровать эти поля) — шифрование не было
  реализовано на тот момент, так что удалять было нечего, кроме `TODO(prod)`-комментария в
  `models/StorageRecord.ts`, который переписан под новое решение. Что всё же стоит сделать
  для продакшена: ограничить вывод этих полей в API только тем ролям, кому он действительно
  нужен (сейчас `/api/records` отдаёт их владельцу/доверенным лицам целиком), и включить
  TLS/HTTPS везде (на Vercel — по умолчанию). Юрлица (`goodsOwner.type === "company"`) этих
  полей не имеют вовсе.
- Паспортные данные и ПИНФЛ **никогда не отправляются через бота** — ни в уведомлении о
  регистрации, ни в сводке владельцу груза (`lib/goodsOwnerBot.ts`); PDF договора, где эти
  поля есть, шлётся адресно конкретному чату (сотруднику при создании записи, самому
  владельцу груза только после подтверждения его номера телефона через `GoodsOwnerLink`).
- Валидация всех форм выполняется дважды: на фронте (для UX) и в каждом API-роуте через
  zod-схемы из `lib/validation.ts` — API не доверяет клиенту.
- dev-bypass для Mini App (`X-Debug-Telegram-Id`) жёстко отключается при
  `NODE_ENV === "production"`.

## Что нужно донастроить руками

1. **Реальный токен бота** — сейчас `.env.example` содержит плейсхолдер. Получить у
   @BotFather и прописать `TELEGRAM_BOT_TOKEN` в Vercel и `.env.local`.
2. **MongoDB Atlas** — создать кластер, пользователя БД, добавить IP-доступ (или `0.0.0.0/0`
   для serverless из Vercel), вставить строку подключения в `MONGODB_URI`.
3. **`NEXTAUTH_SECRET`** — сгенерировать случайную строку (например, `openssl rand -hex 32`).
4. **`APP_BASE_URL`** — прописать финальный домен Vercel-деплоя и выполнить `npm run set-webhook`.
5. **Сменить пароль владельца** — после первого входа сразу сменить `OWNER_PASSWORD`,
   заданный в seed-скрипте, через баннер «Сменить пароль» в панели.
6. Опционально: настроить `/setmenubutton` в @BotFather, чтобы у бота была постоянная кнопка
   меню с Mini App (сейчас кнопка приходит инлайн-сообщением на `/start`).
7. Опционально: зарегистрировать список команд бота через `/setcommands` в @BotFather
   (`start`, `help`, `report`, `contract`) — они и так работают без этого, регистрация только
   добавляет автоподсказку в интерфейсе Telegram.

Новых переменных окружения для частей 2 и 3 не потребовалось — ни отправка уведомлений/PDF
через бота, ни генерация договора не используют внешних сервисов или дополнительных ключей.

## Известные ограничения MVP

- Восстановление забытого пароля веб-панели не реализовано (MVP для одного заказчика с
  небольшим числом пользователей) — пароль сбрасывает владелец/доверенное лицо вручную,
  выдав новый временный доступ через раздел «Доступ» (или напрямую в БД).
- Пагинация в разделе «Записи» реализована на уровне API (`page`/`limit`), но в интерфейсе
  сейчас подгружается первая страница (по умолчанию 50 записей) — для очень больших объёмов
  стоит добавить постраничный UI.
- В `package.json` намеренно оставлена мажорная версия `next@14` (как зафиксировано в ТЗ);
  `npm audit` может показывать advisory по транзитивной зависимости `postcss` внутри самого
  `next` — фикс требует перехода на `next@16` и является breaking change, поэтому не применён.
- Бот не даёт владельцу груза интерактивно выбрать «тот самый» договор/запись из нескольких —
  всегда самая свежая, с пояснением в тексте сообщения (см. «Тип арендатора и договор» выше).
  Полноценный выбор потребовал бы инлайн-кнопок с callback-состоянием — избыточно для MVP.
- Смена типа арендатора (физ. ↔ юр. лицо) при редактировании записи на веб-панели полностью
  заменяет `goodsOwner` новым пустым объектом нужной формы — поля старого типа не
  переносятся (они и не соответствуют друг другу по смыслу).
- `GoodsOwnerLink` не имеет собственного экрана в веб-панели (отвязать/посмотреть привязки
  владельцев груза можно только напрямую в БД) — в ТЗ это не требовалось, отмечено как
  возможное развитие.
- Начисление по тарифу всегда считается по ТЕКУЩИМ значениям `quantity`/`tariff` записи за
  весь период с момента её создания — если количество или ставку правят задним числом, это
  не учитывается как "было по-другому до такого-то числа" (история видна в `AuditLog`, но
  не влияет на расчёт задолженности). Для одного фиксированного тарифа на запись, который
  меняется редко, это разумное упрощение для MVP.
- `lib/debt.ts` при подсчёте задолженности по конкретному владельцу читает все его
  StorageRecord из БД без пагинации — на масштабе одного заказчика это быстро, но при
  очень большом числе записей на одного арендатора стоит перейти на агрегацию в MongoDB
  (`$group`), как уже сделано в `lib/reports.ts` для других отчётов.
- Выбор владельца/контейнера при записи оплаты (`/dashboard/income`) — обычные `<select>` по
  списку существующих связок, без поиска по мере набора текста; для одного заказчика с
  разумным числом арендаторов этого достаточно.
